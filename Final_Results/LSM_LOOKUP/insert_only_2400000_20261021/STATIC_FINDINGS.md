# Source findings (live results pending)

Checkout: `5f2a078eadb8817246f5d500dee2822f826d9c1e`. These are source findings, not measurements. The matrix must finish before live work begins.

1. **Both `merkle_lsm` and the retained upstream-derived `lsm3` are secondary indexes.** Their insert API receives a heap TID; their physical entries are ordinary nbtree `IndexTuple`s, not the ten YCSB payload fields. `ml_insert` calls `btinsert(active,values,isnull,tid,heap,...)` (`contrib/merkle_lsm/merkle_lsm.c:393-418`). `lsm3_insert` does the same, with an uninitialized-top fallback to the base (`Final_Results/LSM_LOOKUP/lsm3_experiment_20261014/lsm3_source/lsm3.c:488-543`). Neither replaces the heap table AM.

2. **There are two separate kinds of Merkle storage.** `usertable_merkle_idx` is an index relation containing its format/routing/build metadata page; it cannot perform ordinary scans (`src/backend/access/merkle/merkle.c:380-448`, `src/include/access/merkle.h:175-195`, `merkleutil.c:999-1060`). Actual aggregate nodes are heap tuples in `ariabc_internal.merkle_node_usertable`, with count, partition, prefix length, leaf flag, eight-byte node ID and 32-byte aggregate hash; three B-trees index these tuples (`merkleutil.c:1640-1659`). The application rows remain in `usertable`.

3. **The auxiliary lookup stores a copied key, not a copied payload.** Its definition is `(merkle_partition_for_hash(merkle_key_hash(ycsb_key),200),merkle_key_hash(ycsb_key),ycsb_key)`, plus the implicit heap TID. There is no `INCLUDE(field1,...)` in the canonical helper (`contrib/merkle_lsm/merkle_lsm--1.0.sql:404-459`). The primary key also duplicates the row's key. It would be inaccurate to say that absolutely no row field is duplicated; the ten text values are not copied into these indexes.

4. **Three-level `merkle_lsm` means five data-bearing B-trees plus one metadata relation.** The public relation is the bulk-built base, with two L0 and two L1 components, not a separate public wrapper plus an additional hidden base (`merkle_lsm.c:270-380`). The metadata relation is a distinct private index AM with a generic-WAL state page (`merkle_lsm.h:29-53`). Its SQL column descriptors resemble the lookup, but its page contents are `MlMeta`, not index entries.

5. **No append-only SSTable write path exists here.** Foreground inserts select only the active L0 B-tree while holding the metadata buffer share lock (`merkle_lsm.c:393-418`). L0 is still a WAL-logged B-tree. `ml_copy` scans a frozen source in key order, searches the destination for the exact `(key,TID)`, then calls `_bt_doinsert` into the existing next-level B-tree (`merge.c:175-257`). Sorted input can improve locality; it does not prove sequential physical offsets. The run/drain/checkpoint offsets must decide that question.

6. **The C node-table search must not be confused with auxiliary lookup scans.** `index_beginscan` in `merkleapply.c:1547` and `:2077` searches `catalog_rel,pkey_idx_rel`, i.e. the aggregate node heap and its primary key. These searches and the direct `table_tuple_update` path do not appear in the outer UPDATE plan. However, split row reconstruction builds a SQL query and executes it using `SPI_execute_with_args` (`merkleapply.c:650-711`); that query is planned and can use the auxiliary lookup. The orchestrator's blanket statement that the internal lookup does not use the planner needs this qualification.

7. **A payload UPDATE remains a Merkle mutation even when HOT.** PostgreSQL can skip ordinary index inserts when `update_indexes` is false. The executor separately captures/removes the old contribution and stages the new contribution; it suppresses the generic Merkle callback during non-HOT ordinary index insertion to avoid double maintenance (`nodeModifyTable.c:2095-2131`). The direct node path updates heap tuples and inserts node index entries only when its own node update is non-HOT (`merkleapply.c:2159-2187`). HOT eligibility does not guarantee every update is HOT; live counters and WAL must establish the fraction.

8. **Hidden children are deliberately excluded from ordinary maintenance.** `ml_hide_component` sets all three `pg_index` flags false (`merkle_lsm.c:205-229`). `RelationGetIndexList` skips `!indislive` (`src/backend/utils/cache/relcache.c:4384-4403`), and `ExecOpenIndices` uses that list (`src/backend/executor/execIndexing.c:172`). Catalog flags, runtime insert-call counts, and WAL will check the actual baseline rather than assuming the helper was used correctly.

9. **An outdated code comment is not the update implementation.** `merkleinsert.c:38-40` says UPDATE calls `ambulkdelete` for the old row. The file's actual `merkleBulkdelete` is a statistics-only VACUUM stub, and the executor implements synchronous UPDATE/DELETE capture. This comment is misleading, not evidence that UPDATE maintains the old entry through VACUUM.

10. **Moving all data into an LSM requires a different storage design.** Replacing the lookup AM alone cannot remove heap versions, TIDs, heap visibility checks, TOAST or the separate aggregate-node heap. A data-holding LSM would need a table access method or equivalent primary storage integration with complete row/version records, MVCC/snapshot visibility, serializable predicate/conflict handling, WAL/crash recovery, deletion/version reclamation, TOAST/large values, and secondary-index row identity. Moving only aggregate nodes into an LSM would be a separate change to Merkle persistence. No engine change is part of this audit.

PostgreSQL indexes are themselves relations (`relkind=i`) with catalog identity and storage. The extra heap relation for aggregate Merkle nodes is distinct from that normal index relation. Moving those nodes inside index pages would also have to preserve commit/abort visibility and rollback currently provided by the heap; it would not remove the application heap.

The current architecture documents already acknowledge the existing-destination B-tree merge, the five-tree scan fanout, separate core Merkle maintenance, and the need to include drain cost. The advisor's sequential-only expectation is stronger than those documents. An absence of random file writes during a short run would not establish an append-only implementation, and random WAL block-reference order is not itself a measurement of physical write order.
