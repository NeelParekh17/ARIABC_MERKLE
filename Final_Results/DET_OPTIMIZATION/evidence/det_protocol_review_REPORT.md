# Deterministic protocol and TPC-C review — 2026-10-07

The current implementation has useful optimizations already, but the saved TPC-C measurements do not establish that its deterministic executor is throughput-optimal or state of the art. Its most promising remaining work is reducing the amount of validation done in a global transaction turn, avoiding unnecessary resimulation, and eventually replacing the global turn with a dependency-aware schedule. Adding workers alone has already stopped helping in the published campaign.

This review inspected current source and independently recomputed the saved v2 accepted results. It also read the original phase traces on ranking (`protectdr@10.129.7.57`) and summarized them in `remote_phase_analysis.json` next to this report, retaining SHA-256 hashes for the input trace files. No build, database, server or benchmark was started, and no protocol source was changed. These are historical measurements of the October 2 campaign, not fresh measurements of the current October 7 checkout. Current source includes newer v3 expected-abort handling and a newer TPC-C harness.

**What the deterministic path actually does**

1. The gateway assigns deterministic transaction sequence numbers and submits requests in order. In the event/block path, `pg_executor::event_loop()` packages prefixed statements into ordered backend blocks. The default preassigned block chunk is 64; block connections can overlap. See `ariabc_pg/src/pg_executor.cxx:5076` and `:5095`. Setting `ARIABC_DET_PREFIXED_DIRECT_PARALLEL=1` does not itself override an enabled event block fast path (`:2301`).
2. Middleware snapshots transaction references, exposes blocks to worker queues in block order, and enqueues their transactions. See `src/backend/bcdb/middleware.c:1835` and `:1875`.
3. Each backend executes SQL speculatively against a PostgreSQL snapshot, captures optimistic writes and records local read/write tags. `get_write_set()` parses the top-level SQL each time; nested static PL/pgSQL statements already benefit from their own plan cache. See `src/backend/bcdb/worker.c:2059`, `:2742`, `:2919`; `scripts/restore_tpcc_procs.sql:85`.
4. The worker waits for its logical turn, checks dependencies on earlier write sets and retries if the captured snapshot is stale. The measured settings select `bcdb_serial_gate_source=0`, so the turn is based on write-set publication, rather than full predecessor PostgreSQL commit. See `worker.c:1296`, `:3041`, `:3054`.
5. The worker publishes its write set and releases the next logical turn BEFORE applying its captured writes and finishing the PostgreSQL transaction. Therefore apply and physical commit already overlap across nonconflicting transactions. This is not a system that simply serializes every PostgreSQL commit. See `worker.c:3084`, `:3100`, `:3107`.
6. After applying writes, and synchronous Merkle deltas when enabled, the worker constructs the result and finishes the PostgreSQL transaction. The normal success path publishes terminal readiness after `finish_xact_command()`. The contiguous committed watermark can advance across successors that already completed, without making each physical commit wait for its predecessor. See `worker.c:3236`, `:3358`, `:3481`, `:3508`; `src/backend/bcdb/raft_apply_ledger.c:1927`; `src/backend/bcdb/shm_block.c:693`.
7. Middleware waits for every result slot in a submitted block, formats completions and marks slots consumed. The event executor then emits ready blocks in submission order. See `middleware.c:1890`, `:1931`; `pg_executor.cxx:4880`. Database commit, committed-prefix advancement, block readiness, Kafka delivery and client completion are separate events.

The non-ledger block path omits ordinary SQL payloads unless `BCDB_BLOCK_RETURN_ACTUAL_RESULTS` is enabled. Safe-ledger transactions force actual payloads; the current code also preserves the reserved expected-abort receipt. The v2 campaign did not explicitly enable ordinary actual-result payloads. Its direct terminal-success counts demonstrate completion, not verification of every returned SELECT value across replicas. `--safedb 1` selects deterministic execution; it is distinct from `--raft-apply-ledger safe`.

**What the saved TPC-C comparison establishes**

Sources: `Final_Results/TPCC/v2_20261002/sweeps/*/accepted.json`, the archived `scripts/sweep_run.sh`, raw gateway logs, settings, table statistics and WAL counters. All 89 accepted measured sweep attempts completed 20,000 transactions and recorded zero permanent failures and divergence. Figures report peaks from unequal numbers of attempts, with substantial stalls in some trials. The following values are peak observations, not stable causal speedup estimates.

|---:|---:|---:|---:|---:|
| 8 | 1,740.14 | 1,430.62 | 1,041.21 | 314 |
| 16 | 3,004.75 | 2,104.38 | 1,507.57 | 666 |

At W100/32, det is about 56.0% of the pg peak, or 44.0% lower. Matching that pg peak would require about 78.6% more det throughput. Increasing det workers from 32 to 64 reduces its best observed TPS by 15.5%, while pg's peak rises by 26.3%. At 32 workers, det rises from 905.92 TPS at W5 to 1,578.57 at W20 and 2,814.97 at W100: contention still matters.

Both paths use SERIALIZABLE, logged tables, fsync, synchronous commit, full-page writes, fillfactor 90 and prewarmed 32GB buffers. However pg is free to find a serial order using SSI and retries, while det must reproduce its prescribed transaction sequence. At W100/32 the peak pg attempt has 2,060 serialization failures versus 1,494 det restarts. Fewer restarts alone do not imply higher TPS: the deterministic turn, dependency waits, capture/apply work and block completion machinery are additional costs. The final pg state need not equal det's because their serial orders differ.

Crucially, these are single-node, same-host, direct-completion runs with `bypassRaft=1`, `waitMajority=0` and `totalNodes=1`. The gateway logs show zero Kafka messages. Optimizing Raft batching or Kafka result delivery cannot explain or directly remove this measured det/pg gap. They must be evaluated separately in a full replicated run.

WAL at the selected W100/32 attempts is 48,453.8 bytes/transaction for det and 48,487.0 for pg: nearly equal. Stock HOT updates are effectively 100% in both. Merkle produces 93,936.7 bytes/transaction and achieves about 70.5% of det TPS. The matched baseline already includes the important fillfactor/HOT optimization. The remaining det gap is not explained by a large increase in WAL bytes, although equal bytes do not establish equal WAL flush latency or grouping.

**Measured remaining work in the deterministic turn**

The following fine timers use integer monotonic-microsecond subtraction and avoid the coarse phase timing bug described below. Values include retries and are averages per completed transaction, not elapsed workload time.

| W100 det peak attempt | 8 workers | 16 | 24 | 32 | 48 | 64 |
|---|---:|---:|---:|---:|---:|---:|
| Serial-slot wait, ms/tx | 1.100 | 2.421 | 3.770 | 5.774 | 12.347 | 21.040 |
| Conflict checks, microseconds/tx | 111.605 | 119.027 | 117.998 | 114.913 | 132.723 | 139.904 |
| Write-set publication, microseconds/tx | 15.010 | 18.550 | 16.572 | 22.849 | 25.398 | 35.791 |

At W100/32 the worker checks about 29.74 write tags and 115.38 read tags per transaction and publishes about 35.54 tags. `conflict_checkDT()` walks lists under the ordered turn; `table_checkDT()` probes partitioned shared maps, normally both A and B after B first becomes nonempty. Exact duplicates are not removed by `rs_table_reserveDT()` or `ws_table_reserveDT()`. Publish-only prefix deduplication scans only the most recent 32 records. See `shm_transaction.c:1195`, `:1227`, `:1250`, `:1404`, `:3223`, `:3368`.

Diagnostic grouping by SQL type suggests Stock-Level averages about 1,018 read checks and 834 microseconds of validation; Delivery averages about 593 read checks, 274 write checks and 593 microseconds of validation. Together these approximately 8% of transactions consume about 48.6% of classified conflict-check time. Thus transaction complexity, especially read/range footprint, can stall the publication turn even when writes do not conflict.

This type attribution is approximate: the W100/32 trace contains 20,000 records but only 19,982 distinct transaction IDs. Source emits the trace using `tx->tx_id` after `delete_tx(tx)` removes the shared hash entry (`worker.c:3524–3528`; `shm_transaction.c:624`). Reuse of the entry can corrupt trace IDs. The grouping excludes duplicate IDs, leaving 19,964 rows, but unique IDs can also be wrong. Aggregate phase counters do not depend on that join. Fix trace identity before using precise per-type attribution as acceptance evidence.

The inspected peak runs report zero parse-barrier wait, zero pre-apply wait, zero tracked apply update/delete wait incidents and zero apply retries. This does not prove all PostgreSQL waits are zero, but it argues against blindly tuning the parse barrier or apply retry budget first. Conditions already use successor-specific condition variables after the spin phase. Merely changing polling to condition variables would repeat an existing optimization.

At W100/32, write-map rotation contributes an average 8.634 microseconds/transaction inside publication, with a 27.274ms maximum clear. This is about 0.173 seconds of accumulated clearing across the 20,000-transaction run, versus 7.104 seconds workload wall time. Rotation is worth addressing for bursts/tails, but eliminating its direct measured time alone does not explain a 1.79x throughput gap.

Filtered coarse finish-phase values are around 3.8ms/transaction. Finish includes result-slot handling, transaction finish, terminal publication and cleanup, so this cannot be called a measured WAL-fsync time. Add separate commit/flush/slot/cleanup measurements before choosing a group-commit change. No final executor profile lines were found in the selected server logs; the v2 harness kills the server with SIGKILL before teardown, so absence of final counters is not proof of zero executor cost.

**Instrumentation must be repaired before optimization claims**

`bcdb_ptrace_delta_us()` in `worker.c:676` casts the nanosecond difference to uint64 before dividing by 1,000. Across a second boundary the negative nanosecond component becomes an enormous positive number. For example, a 200ms interval from 10.9s to 11.1s should yield 200,000us; the current calculation yields approximately 18,446,744,073,909,551us. Coarse phase averages from those CSVs are invalid. The saved analysis flags cells >= 10^12us and excludes them; it never overwrites or silently repairs the historical traces. Filtered means are conditional statistics and should not replace a new correctly instrumented measurement.

There is also substantial measurement overhead: with phase tracing enabled, each two-map tag probe invokes roughly eight timestamp reads, in addition to locks/hash operations. About 145 checks/transaction implies on the order of 1,160 clock reads in validation alone. CSV output is line-buffered per transaction. All v2 runs enable the trace. Compare traced and untraced throughput using the same workload/settings, and use sparse sampling or aggregate counters for published throughput runs. This observation is not a quantified speedup claim.

**Optimization order I recommend**

1. **Reduce validation and publication work without changing the serial order.** Use a compact per-transaction set of exact read/write tags, preserving distinct prefix/full-key tags and checked versus publish-only semantics. Cache each tag hash and store tags contiguously to avoid per-record allocations and pointer chasing. Deduplicate reservations made repeatedly by B-tree/heap/SSI hooks; `PredicateLockAcquire()` currently records BCDB tags before PostgreSQL's own duplicate-lock check (`predicate.c:2433`). Batch lookups by partition where beneficial, while retaining bounded lock hold times. First measure total versus unique tags; saved counters do not reveal the removable duplicate fraction. This is the most concrete low-risk protocol implementation improvement.
2. **Reduce conservative resimulation and the time successors are blocked by a retry.** A stale transaction reaches its turn, detects a conflict, waits for a committed target and reruns SQL before it can publish; every higher ID remains blocked meanwhile (`worker.c:2700`, `:2738`, `:3068`). At W5/32 the peak attempt has 14,761 restarts and about 30.1ms serial wait per transaction. Start by counting conflicts that were already visible to the actual snapshot but remain above the contiguous committed baseline. There is an existing `bcdb_xid_preceded_snapshot()` helper (`shm_transaction.c:1293`), but the inspected `table_checkDT()` does not call it: it only compares transaction IDs to `tx_id_committed`. A conservative committed-XID-before-snapshot test may avoid some needless retries. Quantify eligibility first, and prove slot ownership/XID visibility and repeated-key chains before enabling it. Early validation or dependency-aware retry preparation can help further, but must revalidate before publication.
3. **Replace synchronous full-map clearing with safe generational reclamation.** Move reclamation off the publication critical path using reader-safe generations and an oldest-active-snapshot/retry bound. Preserve conflict history needed by outstanding transactions. Increasing the threshold alone trades memory for less frequent clearing; it is not a complete protocol improvement, and two-map rotation must remain correct across retries and long transactions.
4. **Investigate the finish/commit pipeline while preserving durability.** Separate PostgreSQL commit/WAL flush time, slot-consumption backpressure, committed-prefix advancement, block-result wait and event-loop emission. Improve overlap or batching only where those measurements show a bottleneck. Preserve actual results and postcommit readiness. Disabling synchronous commit, skipping SQL reads, or acknowledging before commit changes the contract rather than establishing a protocol optimization. The existing gateway submits all 20,000 transactions quickly; its 3.68s mean latency at W100/32 is dominated by queued work, not an 11ms database service time. A bounded window can reduce queue latency, but needs its own TPS experiment.
5. **For a large structural gain, build a deterministic dependency schedule.** Within a fixed logical epoch, derive complete row/range dependencies and execute independent ready transactions in parallel while retaining all order-relevant dependencies. Validation can be performed outside a single publication baton if its metadata and snapshot are stable. Row/prefix-level dependencies are preferable to serializing an entire warehouse. Remote Payment and NewOrder supplier accesses, Delivery ranges, customer-by-name searches and empty-range phantoms require cross-warehouse/range edges. A common logical snapshot or equivalently rigorous visibility rule, deterministic tie-breaking, retry dependency expansion and ordered durable/result frontiers are prerequisites. This is a protocol project, not removal of one wait call.
6. **Consider multi-version deterministic reads as a longer-term direction.** PostgreSQL MVCC alone does not give each speculative transaction its prescribed logical view when physical commits overlap. Logical transaction-version visibility could reduce reruns and allow dependency-only waiting, but needs substantial storage/snapshot integration. Existing deterministic systems illustrate the design space: [Aria](https://www.vldb.org/pvldb/vol13/p2047-lu.pdf) executes batches against a common snapshot and can deterministically reorder transactions; [BOHM](https://www.vldb.org/pvldb/vol8/p1190-faleiro.pdf) separates ordering/version creation from execution; [Calvin](https://dsf.berkeley.edu/cs286/papers/calvin-sigmod2012.pdf) uses deterministic scheduling with declared accesses. These are design references, not evidence that their published TPS transfers to this PostgreSQL implementation. Aria-style reordering can change the prescribed serial order and is not automatically compatible with AriaBC's result/recovery contract.

Avoid double-counting already implemented work: row-level composite-key tags, leading-key Merkle routing, HOT-friendly fillfactor, concurrent apply, nonblocking committed-prefix advancement, successor condition variables, block pipelining and pg retry jitter are already present in the measured baseline. SQL plan caching and fewer stock probes are useful secondary work, but cached nested PL/pgSQL plans already exist and the observed top-level parse/plan cost is much smaller than the long waits.

**How to establish a real improvement**

Use ranking for the entire TPC-C pipeline, isolated data directories/ports and a fresh artifact root. Preserve the historical v2 workload for direct v2 A/B comparison, and separately use the current v3 workload/SQL for current behavior. V2's generator uses uniform customer/item selection, 1% remote NewOrder transactions with one remote line, and no expected invalid-item rollback injection; its older Stock-Level SQL excludes the upper order bound. V3 changes those semantics, adds deterministic timestamps and expected rollback handling, and requires a 60-second warmup and at least 300-second window. Therefore v3 versus v2 TPS is not a code-only optimization comparison. Inspect `scripts/generate_tpcc_workload.py:98`, `:199`; `scripts/restore_tpcc_procs.sql:731`; `scripts/tpcc_v3/tpcc_procs.sql`; `scripts/distributed/tpcc_v3/run.sh:17–36`.

For each candidate, alternate unchanged baseline/candidate runs with identical binary/source provenance, workload hash, physical reset, routing, fillfactor, durability, CPU/NUMA placement and measurement instrumentation. Start with W100/32 to test baseline overhead, W5/32 to test contention and W100/64 to test scalability. Use equal repetition budgets and report median, spread and peak. Record validation checks versus unique tags, retry reason/eligibility, time between publication handoffs, commit/flush waits, WAL/transaction, CPU, context switches, block readiness and result-slot occupancy.

Single-node acceptance needs terminal counts, zero unexpected permanent failures/divergence, expected-abort accounting on v3, invariant checks and sufficiently complete final-state comparisons. Merkle variants need native verification. Protocol changes additionally need replicated lab-host validation, prescribed-order actual-result checks, full replica-state/root comparisons and failure/replay tests including repeated INSERT/DELETE chains and result-ring reuse. The old eight-table count/hash-sum projection excludes timestamps and immutable item; matching it is useful diagnostic evidence, not a full determinism proof. Preserve all artifacts and do not claim improved TPS until both performance and correctness acceptance pass.

The first implementation I would pursue is exact tag deduplication with cached hashes and compact storage, after fixing trace duration and transaction identity. The first major protocol redesign I would pursue is deterministic dependency scheduling. No TPS gain from either has been measured in this review.
