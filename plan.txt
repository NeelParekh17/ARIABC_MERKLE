### What Algorithm 1 actually says

The paper’s flow is roughly:

```text
Run_Tx(Tk):

1. Atomically take snapshot S
2. Record check_from_id = last_committed_tx_id + 1
3. Execute transaction on snapshot S to collect rw_set
4. While not all previous txns up to k-1 have committed:
      wait for commit signals
      latest_commit_id = last_committed_tx_id
      CheckConflict(oldest_commit_id, latest_commit_id, rw_set_k)
      oldest_commit_id = latest_commit_id
      if conflict: restart
5. Commit(Tk)
6. Broadcast commit signal
```

The paper explicitly says the transaction executes on snapshot `S` to determine its read/write set, without committing updates yet. Then it waits for commit signals from preceding transactions and checks conflicts against transactions whose read/write sets became available after they committed. Finally, `Commit(Tk)` stores the read/write set in the global table and advances `last_committed_tx_id`.  

So Algorithm 1 is **not**:

```c
wait until T_{k-1} fully commits;
then do one conflict check;
then apply;
```

It is more like:

```c
execute first;
then incrementally wait/check committed predecessors;
then commit once all predecessors are checked;
```

Your pasted trace says your current paper mode does this:

```text

```

and the code path confirms that `bcdb_wait_for_prev_committed(tx)` runs before `conflict_checkDT()` in the last-committed gate mode, while `publish_ws_tableDT(tx->tx_id)` runs in both modes. 

That is **correctly conservative**, but it collapses Algorithm 1’s incremental loop into one big wait. Tiny but important dragon-scale difference.

### So is the gate condition wrong?

For **correctness**, no.

For **“exact paper Algorithm 1” fidelity**, yes, slightly.

Your gate:

```c

```

means:

```text
Do not conflict-check until every predecessor up to tx_id - 1 has committed.
```

Algorithm 1 means:

```text
Conflict-check chunks of predecessors as commit signals arrive.
```

So your mode is stricter than the paper. I would name it:


### Is the finish phase wrong?

Probably not, assuming this ordering is true:

```c

```

In strict paper mode, direct:

```c

```

is fine because your earlier gate guarantees no successor can overtake. T3/CAS is needed only when apply completion can happen out of order.

### One subtle thing to check

In the paper, the committed transaction’s read/write set becomes visible as part of `Commit(Tk)`, then `last_committed_tx_id` advances. In your code, `publish_ws_tableDT(tx->tx_id)` happens **before apply + commit**.

In strict paper mode, that is usually harmless because successors are waiting on `last_committed`, so they cannot observe/use that write-set until after the predecessor commits anyway. But it means your implementation is not literally the paper’s ordering. It is logically equivalent only because the strict gate hides the early publication.

### Why your 2.6× slowdown is meaningful

Yes, the slowdown is meaningful, but phrase the claim carefully:

Not quite:

Because exact Algorithm 1 already allows some incremental conflict-check overlap. Your strict version waits for the whole predecessor chain before doing conflict check.

## Change 3: Add the paper-style wait/check helper

Add this in `worker.c`:

```c
static int
bcdb_paper_wait_and_check(BCDBShmXact *tx, BCBlock *block)
{
    BCTxID oldest_commit_id;
    BCTxID latest_commit_id;
    BCTxID target_commit_id;
    int rw_conflicts = 0;

    /*
     * Algorithm 1:
     * oldest_commit_id was captured before snapshot / optimistic execution.
     *
     * In your code, activeTx->tx_id_committed is already set before
     * get_write_set(), so it represents the snapshot baseline:
     *
     *     oldest_commit_id = last_committed_tx_id at snapshot time
     */
    oldest_commit_id = activeTx->tx_id_committed;
    target_commit_id = tx->tx_id - 1;

    while (oldest_commit_id < target_commit_id) {
        /*
         * WaitForCommitSignals().
         *
         * Important: wait only until last_committed advances beyond
         * oldest_commit_id, NOT until tx_id - 1.
         */
        PTRACE_BEGIN(BCDB_PHASE_GATE);
        latest_commit_id =
            bcdb_wait_until_commit_advances(tx, block, oldest_commit_id);
        PTRACE_END(BCDB_PHASE_GATE);

        if (latest_commit_id > target_commit_id)
            latest_commit_id = target_commit_id;

        /*
         * CheckConflict(oldest_commit_id, latest_commit_id, rw_set_k).
         *
         * Minimal version:
         * temporarily move the lower bound so conflict_checkDT()
         * checks only newly committed predecessors.
         *
         * Cleaner version:
         * implement conflict_checkDT_range(oldest, latest).
         */
        PTRACE_BEGIN(BCDB_PHASE_CONFLICT);

        activeTx->tx_id_committed = oldest_commit_id;

        /*
         * If your conflict_checkDT always checks up to current
         * last_committed_tx_id, this is still safe, but slightly less exact.
         * For exact paper behavior, add an upper bound latest_commit_id.
         */
        rw_conflicts = conflict_checkDT();

        PTRACE_END(BCDB_PHASE_CONFLICT);

        if (rw_conflicts)
            return 1;

        oldest_commit_id = latest_commit_id;
    }

    return 0;
}
```

Then add the helper it calls:

```c
static BCTxID
bcdb_wait_until_commit_advances(BCDBShmXact *tx,
                                BCBlock *block,
                                BCTxID old_commit_id)
{
    BCTxID latest;
    uint64 wait_start_us = bcdb_get_time();
    uint64 next_warn_us = wait_start_us + 5000000;
    int spins = 0;

    for (;;) {
        latest = get_last_committed_txid(tx);

        if (latest > old_commit_id)
            return latest;

        /*
         * Poll/sleep version.
         * This matches the paper's "periodic or count-based or combination"
         * wait idea.
         */
        if (++spins < 128) {
            pg_spin_delay();
        }
        else {
            pg_usleep(64);
        }

        if (bcdb_get_time() >= next_warn_us) {
            ereport(LOG,
                    (errmsg("[BCDB_PAPER_WAIT] txid=%d old_commit=%d last_committed=%d waited_us=%lu",
                            tx->tx_id,
                            old_commit_id,
                            latest,
                            (unsigned long)(bcdb_get_time() - wait_start_us))));
            next_warn_us += 5000000;
        }
    }
}
```

This is the heart transplant. Your old wait function waits for the whole bridge to clear. This one waits for one or more cars to move, checks, then waits again.

## Change 4: For exactness, add an upper-bound conflict check

The better version is not:

```c
conflict_checkDT();
```

It is:

```c
conflict_checkDT_range(oldest_commit_id, latest_commit_id);
```

Because Algorithm 1 calls:

```text
CheckConflict(oldest_commit_id, latest_commit_id, rw_set_k)
```

The paper pseudocode explicitly passes both lower and upper transaction IDs into `CheckConflict`. 

So add this wrapper:

```c
static int
conflict_checkDT_range(BCTxID from_exclusive, BCTxID to_inclusive)
{
    /*
     * Best implementation:
     * teach table_checkDT/ws lookup to ignore committed write-set records with:
     *
     *     writer_txid <= from_exclusive
     *     writer_txid >  to_inclusive
     *
     * Return conflict only when:
     *
     *     from_exclusive < writer_txid <= to_inclusive
     */
}
```

Then the paper loop becomes:

```c
rw_conflicts =
    conflict_checkDT_range(oldest_commit_id, latest_commit_id);
```

If you want a **minimal patch first**, you can temporarily keep `conflict_checkDT()` and only use the incremental wait loop. That will be safe, but not perfectly Algorithm 1 if `conflict_checkDT()` cannot limit the upper bound.

## Change 5: Move `publish_ws_tableDT()` in paper-exact mode

For `BCDB_GATE_SRC_PAPER_EXACT`, do **not** publish here:

```c

```

Instead publish during finish, after successful apply, immediately before advancing `last_committed`.

Your finish phase should become:

```c

    /*
     * At this point:
     * - optimistic execution succeeded
     * - conflict checks against all predecessors succeeded
     * - apply succeeded
     *
     * Now make this transaction visible to later transactions.
     */
    publish_ws_tableDT(tx->tx_id);

     * Make sure ws publication is visible before the commit watermark.

    pg_write_barrier();

    ConditionVariableBroadcast(&block->condCommit);

    set_last_committed_txid(tx);
}
else if (bcdb_advance_commit_watermark) {
    advance_last_committed_txid(tx);
}
```

Important: only do this after you are sure the PostgreSQL apply/commit path has succeeded. If apply fails and you already published the write-set, later transactions may see a ghost transaction. Ghosts belong in haunted houses, not conflict tables. 👻

## Final paper-exact flow

After changes, `paper_exact` should look like this:

```text
retry_loop:

  oldest_commit_id = get_last_committed_txid()
  activeTx->tx_id_committed = oldest_commit_id

  snapshot = GetTransactionSnapshot()

  rw_set_k = get_write_set(tx, snapshot)

  while oldest_commit_id < tx_id - 1:
      wait until last_committed_tx_id > oldest_commit_id
      latest_commit_id = last_committed_tx_id

      conflict = CheckConflict(oldest_commit_id,
                               min(latest_commit_id, tx_id - 1),
                               rw_set_k)

      if conflict:
          restart transaction with new snapshot

      oldest_commit_id = latest_commit_id

  apply buffered writes

  publish_ws_tableDT(tx_id)

  set_last_committed_txid(tx_id)

  broadcast commit signal
```

This is the version I would call:

```text
paper_exact
```

Your current version should be called:

```text
paper_strict
```

And Lever D remains:

```text
leverd = publish write-set before apply, then let successor conflict-check early
```

One final practical warning: turn `bcdb_dt_conflict_tracking=on` during these tests. Your architecture doc says conflict tracking is an active GUC but defaults to `off`, and with it off the “paper algorithm” becomes mostly a commit-ordering benchmark rather than an Aria-style read/write conflict benchmark.
