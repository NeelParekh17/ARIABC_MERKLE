## 1. Root cause diagnosis from the data

### 1.1 The serial gate is the choke point, not the optimistic phase

With `bcdb_worker_count = 12`, you have 12 workers running optimistic executions concurrently. But the serial gate requires:
```
get_last_committed_txid() + 1 == tx->tx_id
```
This is a global strict ordering barrier — only one transaction can hold the commit slot at a time. No matter how many workers finish their optimistic phase, they all pile up at this gate waiting for the previous `tx_id` to broadcast `ConditionVariableBroadcast`. So:

- More gateway threads → more transactions in the queue → more workers reaching the serial gate simultaneously → more processes woken by each broadcast, only 1 proceeds, 11 immediately sleep → **thundering herd on the condition variable**
- The 4-thread sweet spot is where the feed rate matches the serial drain rate
- Beyond 4 threads the queue always has a backlog → latency rises → TPS drops

The workload B CV% at 16 threads (7.1%) vs 4 threads (0.38%) is the smoking gun for this — that variance is the signature of irregular broadcast storms under load.

### 1.2 `synchronous_commit` is ON — the most damaging config error

The line `#synchronous_commit = off` in postgres.conf is commented out, so PostgreSQL uses the default value: `synchronous_commit = on`. This means every call to `finish_xact_command()` in the serial phase waits for WAL to be physically flushed to disk before returning. This happens **for every single committed transaction in the serial gate**.

The serial stall window is: `serial_apply_time + WAL_flush_time`. With sync_commit on, WAL flush time extends the window during which all other workers are blocked at the gate. Disabling it removes the disk I/O from the critical serialization path entirely, since BCDB gets its correctness guarantee from Merkle trees, not from WAL durability.

### 1.3 Zero retries is a false positive

Every run shows `mean_retries_total = 0` and `mean_serialization_retries = 0`. This doesn't mean there are no conflicts. The CSV tracks gateway-level retries (reconnects, permanent failures). Internal BCDB retries — where `bcdb_worker_process_tx_dt()` aborts the optimistic attempt and reruns from a fresh snapshot — are invisible to this metric. The workload B skew would certainly produce internal conflicts, especially at 12+ gateway threads flooding hot keys.

### 1.4 Workload A row count confirms unique-insert correctness

Workload A ends at exactly 12,498 rows consistently with the same Merkle root hash `125a1b...` across all 3 runs at every thread count. A workload named `insert12k-uniq` landing at 12,498 rows means ~12k of the 20k transactions were inserts, and they were unique. The deterministic execution is working: same hash every time regardless of thread count — this is the correctness guarantee holding perfectly.

### 1.5 Workload B at 1 thread shows the baseline serial cost

At 1 thread workload B takes 10.44s vs workload A's 8.51s. The extra ~2s for the same 20k transactions reveals the cost of the skewed workload's mixed read/write pattern — more conflict potential, more time at the serial gate per transaction because hot keys create longer conflict chains.

## 2. Immediate config changes

These cost zero code change and deliver real gains.

### Change 1: Turn on async commit — the single highest ROI change

```conf
synchronous_commit = off
```

Remove the `#` comment. This eliminates the WAL fsync wait from the serial gate critical path. `finish_xact_command()` will return as soon as writes are applied to shared buffers; the WAL writer flushes asynchronously in the background. For BCDB, this is safe: the Merkle tree's XOR state in shared buffers is immediately visible and consistent; WAL durability is not what provides integrity guarantees here.

Expected gain: the serial stall window shrinks from `apply_time + fsync_time` to just `apply_time`. On NVMe SSD, a single WAL flush is ~0.2–0.5ms. Over 5000 TPS, that's 1000–2500ms of serial gate stall removed per second — a direct multiplier on commit throughput. Estimated improvement: 15–35% TPS, with the larger gain on workload B (skewed = more serial-gate congestion per commit).

Also add:
```conf
wal_writer_delay = 10ms          # flush async WAL more frequently than 200ms default
commit_delay = 0                  # no artificial commit batching delay
```

### Change 2: Scale Merkle partitions to match your workload

```sql
DROP INDEX usertable_merkle;
CREATE INDEX usertable_merkle ON usertable
  USING merkle(ycsb_key)
  WITH (partitions = 200, leaves_per_partition = 8, fanout = 2);
```

Current default (58 partitions × 4 leaves = 232 leaves) gives ~54 rows/leaf for 12k rows. With the skewed workload B, hot rows cluster into the same leaves, increasing Merkle write-set conflict probability. With 200 × 8 = 1600 leaves, average density drops to ~7.5 rows/leaf — dramatically reducing the chance that two concurrent updates land in the same Merkle partition. This directly reduces the retry rate for internal BCDB conflicts on the Merkle index path.

The `HASHTAB_SWITCH_THRESHOLD = 200 * NUM_WORKERS = 200 * 12 = 2400`. With `MAX_TX_PER_BLOCK = 5500`, a block can trigger one shard flip mid-block. This is fine but worth knowing.

### Change 3: Tune worker count per workload

```conf
bcdb_worker_count = 8   # for workload B (skewed)
```

The data shows peak throughput at 4 gateway threads. With the serial gate as the bottleneck, optimal worker count ≈ `serial_TPS × mean_optimistic_phase_duration`. For workload A at 5478 TPS and an optimistic phase taking roughly 1.5ms, optimal workers = 5478 × 0.0015 ≈ 8. For workload B at 4200 TPS, it's even lower. Having 12 workers when the serial drain rate supports ~8 means 4 workers are always idle at the gate, consuming memory and condition variable broadcast overhead with no benefit.

For workload A (uniform, insert-heavy), keep at 10–12. For workload B (skewed, mixed), try 7–8.

### Change 4: Raise `bcdb_result_ring_slots` cautiously

```conf
bcdb_result_ring_slots = 256
```

The current 128 slots is fine for these workloads (20k txns, 12 workers means ~1666 txns per worker, cycling through the 128-slot ring many times). But for larger batch sizes approaching `MAX_TX_PER_BLOCK = 5500`, 128 slots can cause a worker to overwrite a result before middleware packages it. 256 costs only a doubling of the result ring memory (negligible) and removes this edge case.

## 3. Code-level changes for correctness and throughput

### Change 5: Advance `last_committed_txid` before `finish_xact_command` with async commit

This is the pipelining opportunity that async commit unlocks. Currently in the serial apply path:
```c
apply_optim_writes();
finish_xact_command();            // blocks on WAL if sync commit is ON
set_last_committed_txid(tx);      // only then wake next waiter
ConditionVariableBroadcast(&block->cond);
```

With `synchronous_commit = off`, `finish_xact_command()` returns immediately after marking buffers dirty — the WAL write happens in the background. There is therefore no correctness reason to delay `set_last_committed_txid()` until after it. The writes are in shared memory and visible. You can advance the ordering as:

```c
apply_optim_writes();
set_last_committed_txid(tx);      // wake next waiter BEFORE finish_xact_command
ConditionVariableBroadcast(&block->cond);
finish_xact_command();            // let this happen while next tx is already in serial apply
```

This pipelined approach lets transaction N+1 start its serial apply while transaction N's `finish_xact_command()` is still running. The two serial applies don't overlap (N+1 can't start heap writes until it gets the broadcast), but the commit overhead is pipelined. This is the BCDB equivalent of PostgreSQL's group commit optimization.

The BCDB architecture doc already notes: "The ordering here matters. The code explicitly moved `set_last_committed_txid()` to after `finish_xact_command()`..." — that note is specifically about sync commit being on. With async commit enabled, moving the broadcast earlier is safe and correct.

### Change 6: Read-only transaction bypass of the serial gate

This is the highest-impact architectural change for workload B, which has heavy reads. Read-only transactions (pure SELECT with no DML) do not modify heap pages, indexes, or Merkle state. They don't need to hold the serial commit slot — they just need a snapshot that includes all committed transactions up to their tx_id.

Current flow for a read-only tx:
```
queue → optimistic execute (gets snapshot, runs SELECT) → wait for serial gate → publish empty write-set → finish_xact_command → advance counter
```

Proposed fast path:
```
queue → detect read-only (no entries in ws_table_record after PortalRun) → 
wait until get_last_committed_txid() >= tx_id - 1 → 
copy result to ring → 
set_last_committed_txid if needed → skip straight to done
```

The key insight: a read-only transaction that executed on snapshot S, where all transactions before it in the log have committed (are visible in S), has a correct result. It doesn't need to write-set-publish or hold the gate. It just needs to confirm the transactions it depends on have committed, which it can check against `get_last_committed_txid()`.

This keeps the serial ordering for results (the result ring slot is still written in tx_id order) while eliminating the commit gate overhead for reads. For workload B with substantial reads in the mix, this could add 20–40% TPS by freeing the serial gate for write transactions.

The implementation requires:
- Detecting read-only: check `list_length(rs_table_record) > 0 && list_length(ws_table_record) == 0` after `get_write_set()`
- A lightweight wait: spin/sleep until `get_last_committed_txid(tx) >= tx->tx_id - 1`
- Skip `publish_ws_tableDT` and `apply_optim_writes` (both no-ops for reads)
- Still advance `last_committed_txid` correctly — tricky since the gate must be claimed, committed, and released atomically even for reads, or the counter stalls

The counter advancement is the delicate part: if read-only transactions skip `set_last_committed_txid()`, any write transaction with a higher tx_id will stall forever waiting for the read tx to advance the counter. So read-only transactions still need to claim and release the counter slot — they just don't need to do any actual DML or index work while holding it. The time they hold the gate becomes negligible (just an atomic write + broadcast, no disk or buffer I/O).

### Change 7: `HASHTAB_SWITCH_THRESHOLD` vs `NUM_WORKERS` relationship

The architecture doc states:
```
HASHTAB_SWITCH_THRESHOLD >= 2 * NUM_WORKERS - 1
```
With `NUM_WORKERS` hardcoded = 2 in `globals.h`, the threshold is `200 * 2 = 400`. But you now have `bcdb_worker_count = 12` as a runtime GUC. If the GUC properly sets the runtime worker count but the threshold was computed at compile time against `NUM_WORKERS = 2`, the threshold of 400 is undersized for 12 workers.

The requirement `>= 2 * N - 1` for N workers means you need threshold >= 23 for 12 workers. 400 is well above that, so this particular invariant is satisfied. But if `NUM_WORKERS = 2` is what actually controls how many worker backends are spawned at init time, and `bcdb_worker_count = 12` is the GUC that sets `blksize` in the sentinel block — then you may have a mismatch: only 2 actual worker processes are running, each handling multiple queue slots, not 12 independent processes. This needs verification in `middleware.c` where `idle_worker_list_init()` uses `NUM_WORKERS` directly. If it does, your 12-worker GUC config isn't actually spawning 12 worker backends.

## 4. Architecture changes for sustained scaling

### Change 8: Group commit at the serial gate

Instead of broadcasting after every transaction individually, when a worker holds the serial gate it should check if the next 1–3 transactions are also ready (optimistic phase complete, write-set published locally) and have no conflicts with the current transaction. If so, apply all of them in a single batch before one broadcast and one `finish_xact_command`. This amortizes:
- The condition variable broadcast cost (from N broadcasts to 1)
- The WAL flush cost (from N flushes to 1 with sync commit off — WAL records from multiple transactions get coalesced into one write)

Implementation sketch in the serial apply loop:
```c
/* current single-tx path: */
apply_optim_writes(tx);
set_last_committed_txid(tx);
ConditionVariableBroadcast(&block->cond);

/* group commit path: */
pending = collect_ready_nonconflicting_txs(tx, max_group_size=4);
foreach(t in pending) apply_optim_writes(t);
foreach(t in pending) set_last_committed_txid_to(t->tx_id);
ConditionVariableBroadcast(&block->cond);  /* one broadcast for all */
```

The conflict check is already available — `conflict_checkDT()` can be called for each candidate with the accumulated write-set of already-applied group members. The maximum group size of 3–4 is conservative enough to avoid starvation of later transactions.

### Change 9: Separate result ring from serial ordering

Currently `bcdb_result_ring_slots = 128` but the result slot is written by the worker after the serial gate. The result text is generated during optimistic execution (in `printtup.c`, written to `sentinelBlock->result[tx_id % (2*blksize)]`) and then copied to the committed slot after the serial gate. This copy is extra work in the critical serial section.

A cleaner design: let the optimistic result live in the temporary slot permanently, and have middleware read it directly indexed by `tx_id` without the copy. This saves one memcpy per transaction from the serial critical path. For 1024-byte result slots at 5000 TPS, that's 5MB/s of unnecessary copying through the serial gate.

## 5. Paper inaccuracies found in light of this data

### 5.1 The performance model in the paper doesn't match this config

The paper says "peak performance of around 5000 TPS" with the deterministic model on a 16-core AMD machine. Your data shows 5478 TPS peak — which is actually above the paper's reported peak. But you're running with `bcdb_worker_count = 12`, Merkle verify passing at 100%, and zero permanent failures. The paper's 5000 TPS was achieved with unspecified worker count and partition config.

More importantly, the paper's Figure 8 shows throughput continuing to rise with thread count before saturating — your data shows it *peaks at 4 and then declines*. This discrepancy suggests the paper's experiments either:
- Used a different (lower) worker count where 4 was not yet the saturation point
- Had `synchronous_commit = off` already enabled, giving a higher per-commit throughput and shifting the saturation point right
- Ran on a different workload block size

### 5.2 Paper claims retries are visible to clients — your data says no

The paper (Section 5.2.1) discusses transaction results being compared at the client. Your gateway metrics show zero retries at the client layer while internal BCDB retries are invisible. The paper's passive detection scheme relies on comparing results across replicas — but if retries are invisible to the gateway and the final result is always deterministic (same Merkle root hash every run), passive detection at the gateway layer would not catch a non-deterministic retry that produced a different intermediate state but the same final committed result. This is a subtle correctness gap the paper doesn't address.

### 5.3 Condition variable broadcast — the paper ignores wake-storm overhead

The paper's analysis of Merkle tree overhead (Figure 10) shows near-zero impact. But it doesn't separate Merkle from serial-gate overhead. Your CV% data shows the serial gate waking 12 workers per commit at high thread counts is the actual performance bottleneck, not Merkle tree I/O. The paper's Figure 10 conclusion ("Merkle overhead is minimal because nodes are buffer-resident") is correct but incomplete — the serial gate condition variable becomes the dominant overhead at high concurrency, not Merkle I/O.

## 8. One more code inaccuracy worth flagging

Looking at the BCDB architecture doc section 8.5: `merkle_record_update()` and `apply_merkle_changeset()` are declared in `shm_transaction.h` but have no implementations. The live code does Merkle updates inline inside `apply_optim_*()`. This means anyone reading the header as documentation will think there's a clean Merkle update API and try to call those functions — which will fail to link. The declarations should either be implemented or removed to prevent confusion for future contributors.

Also: `bcdb_serial_gate_mode = 1` in your config implies at least modes 0 and 1 exist. The architecture doc doesn't describe what mode 0 does. If mode 0 is the non-DT path (which the doc says uses `ws_table_check()` against maps that are never populated), running with `bcdb_serial_gate_mode = 0` would silently disable conflict detection and appear to work while allowing non-deterministic commits. That's a silent correctness failure with no error message — worth adding a `ereport(WARNING, ...)` in the mode-0 path that says conflict maps are not populated, so the non-DT path is effectively no-conflict.
