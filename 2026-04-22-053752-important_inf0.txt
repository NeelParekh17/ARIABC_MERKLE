  Why this races:

  The serial gate ensures txs enter apply in order, but apply phases overlap
  (that's the whole point of Lever D v2). A fast tx_13 (SELECT, 1ms apply) can
  complete Steps 10+11 before a slow tx_10 (UPDATE, 50ms apply) finishes apply
  and reaches Step 10. When slot_13 fires, slot_10 may be zeroed or have the
  previous block's stale result.

  When it masks in practice:

  YCSB/TPCC benchmarks use uniform transaction types within a block, so all txs
  finish apply at roughly the same time. The race is unlikely to fire but is not
   prevented by any memory ordering — it's a genuine bug.

  The correct fix is one line — swap the wait function:

  // Replace:
  bcdb_wait_until_slot_ready((BCTxID) last_tx_id);

  // With:
  bcdb_wait_until_committed((BCTxID) last_tx_id);

  (set_last_committed_txid) is strictly serial and always comes after Step 10

  0–13 are all written.

  ---
  "serializes commit order by waiting for the predecessor"

  This is bcdb_wait_for_prev_committed(tx). Because Lever D v2 lets apply phases

  Watermark (last_committed_tx_id) — batch readback

  The current middleware collects ALL results in one shot:
  enqueue tx_0..tx_N → wait for watermark ≥ N → read all N slots → return
  One wait, one batch response. Simple and correct. This is what the benchmark
  exercises.

  ---
  Per-slot (result_committed_txid[slot]) — designed for streaming

  Imagine a block of mixed-cost transactions:
  tx_0: complex UPDATE  (apply = 50 ms)
  tx_1: simple SELECT   (apply =  1 ms)
  tx_2: simple SELECT   (apply =  1 ms)

  With watermark-only readback, the client sees ALL results at ~50 ms — tx_1 and
   tx_2 are done at 2 ms but the client can't know that, because
  last_committed_tx_id hasn't advanced yet (tx_0 is still applying).

  With per-slot streaming, a middleware that polls each slot independently can
  return tx_1 and tx_2's results at ~2 ms and tx_0's at ~50 ms. Each
  transaction's result becomes available the moment IT commits, with no
  dependency on predecessors.

  ---
  Why T3 per-slot exists in the codebase right now:

  It's infrastructure for a streaming API that hasn't been wired up yet. The
  intended future path was:

  1. Middleware polls result_committed_txid[slot_i] for each tx independently
  2. Returns each result to the client as soon as that individual tx fires
  3. advance_last_committed_txid (also infrastructure, never called) replaces
  the serial chain — the fastest-finishing tx amortises the watermark advance
  for all already-committed successors via a CAS prefix scan

  Together, T3 + advance_last_committed_txid would eliminate the O(N) serial
  bottleneck entirely. Currently neither is fully wired in — the watermark still
   advances through the serial chain at Step 11, and the benchmark pays that
  cost.

● No. Let me explain exactly why, because the distinction is important.

  ---
  What actually guarantees determinism:

  The determinism guarantee (same Merkle hash on every node) comes from
  execution order, which is enforced by the serial gate (published_max_tx_id).
  tx_N can only enter apply after tx_{N-1} publishes its write-set. The gate
  forces strict tx_id ordering of applies. This is unchanged by
  advance_last_committed_txid.

  last_committed_tx_id is a derived indicator — it reflects what has already
  happened, it doesn't control the order things happen in.

  ---
  What advance_last_committed_txid actually changes:

  Only WHEN the watermark number gets updated. Instead of tx_5 waiting for tx_4
  to call set_last_committed_txid before advancing, tx_5 tries a CAS and scans
  forward to advance the watermark past already-committed successors. PostgreSQL
   commits (finish_xact_command) still happen in the same order — just the
  counter catching up to them is no longer serialized.

  ---
  The one real caveat — conflict tracking:

  When bcdb_dt_conflict_tracking=on, the conflict check uses tx_id_committed = 
  get_last_committed_txid() as a lower bound — txs at or below the watermark are
   assumed to be in the current snapshot, so no conflict check needed against
  them.

  If the watermark jumps from 4 to 8 (because 5,6,7,8 all committed quickly),
  tx_9's conflict check would skip txs 5–8 — but those txs committed AFTER
  tx_9's snapshot was taken, so their writes are NOT in tx_9's snapshot.
  Skipping the conflict check against them could miss a real within-block
  write-write conflict.

  However this is not a silent correctness failure — those conflicts would
  surface as heap-level lock contention during apply and get caught by the apply
   retry loop, just less efficiently.

  And critically: bcdb_dt_conflict_tracking is off by default — the conflict
  check is a no-op in the default configuration, so this caveat doesn't apply at
   all to the current benchmark setup.
